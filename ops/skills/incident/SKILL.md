# Incident 流程

站点相关的值（SSH 目标、日志路径、数据库连接）写成占位符，**站点私有值见私有运维仓**：
`<ssh_target>`、`<deploy_dir>`、`<service>`、`<nginx_error_log>`、`<nginx_access_log>`。

原则：

1. **先恢复站点，再查根因。** 不接受「还在定位，所以先不动」。
2. 每个缓解动作：先备份、能一条命令回滚、前后用同一组探测对照。
3. 缓解实测无效就回滚，并如实报告，不要把无效的改动留在线上。
4. 根因必须有运行时证据（日志行、SQL 结果）；证据链没闭合不下结论。
5. **确认口径与 deploy 对齐。** 可回滚的小配置（开关、路由、调度状态这类，备份后一条命令就能还原）
   先动手再汇报；镜像回滚、重启服务、删除数据不适用，走 `ops/skills/deploy/SKILL.md` 的逐步确认流程：
   每一步先说明要做什么、影响面、怎么回滚，等人明确同意，一次确认不延续到下一次。
   需要重启才生效的改动（配置文件 / 环境变量来源的开关）按「重启服务」处理，先确认。

## 1. 止血：先让用户侧恢复

1. 5 分钟内能拿到的信息：`/health`、容器状态、最近一次部署或配置变更（最常见的原因）、
   磁盘和内存、`<nginx_error_log>` 末尾。
2. 按破坏性从小到大选可回滚的手段：
   - 绕过有问题的中间层（切回直连）；
   - 把拦截类功能的总开关切到观察模式（配置文件 / 环境变量来源的开关要重启才生效）；
   - 暂停调度或降权某个账号 / 上游（不要直接删除）；
   - 回滚到上一版镜像（见 `ops/skills/deploy/SKILL.md` 第 8 节；属于原则 5 里要逐步确认的操作）；
   - 限流或挂维护页。
3. 缓解后用同一组探测验证，并汇报：改了什么、回滚命令、效果。
4. 压测或探测要用真实 key。假 key 会让上游提前关连接，容易把它误判成中间件缺陷。

## 2. 分层定位：nginx 边缘 / 应用 / 上游

同一个状态码在不同层含义不同，先判断是哪一层产生的：

| 层 | 特征 | 看哪里 |
|---|---|---|
| nginx 边缘 | 只出现在 nginx error.log，不进应用日志：`limit_req` / `limit_conn` 限流、边缘拦截规则、upstream 超时、CDN 超时 | `<nginx_error_log>`、`<nginx_access_log>` |
| 应用 | 应用日志里有这次请求；延迟约 1ms 的 429 是应用层并发限制，没打到上游；5xx 带行号的 ERROR | `docker compose logs <service>`、`ops_error_logs`、`usage_logs` |
| 上游 | 应用日志里有上游往返、`upstream_status_code`、failover 记录；上游并发限制、403、503 | 管理端 ops 错误日志里的 `upstream_errors`、上游控制台 |

1. 用 `client_request_id` / 上游 request id 把三层日志串起来。
2. 逐层探测：直连应用端口、经 nginx、经公网域名，用同一个请求各打一遍，找出从哪一层开始出错。
3. 429 先判断来自哪一层再决定要不要处理；它经常是限流在正常工作，不是故障。
4. 部署后部分用户白屏、其他人正常：先看是不是旧标签页请求旧 chunk 404（`ops/skills/deploy/SKILL.md` 第 5 节）。

## 3. 按 account_id 拆指标

对「时间段 A 和 B 对比」（缓存命中率、成功率、延迟、单请求成本）：**必须按 `account_id` 拆开**，
并区分「账号内效应」和「份额转移效应」。账号池里各账号指标差异大、份额还在转移，
全池聚合值可能只是份额变化造成的假象（辛普森悖论）。同样适用于按 group、model、channel 聚合。

```sql
SELECT account_id,
       count(*)                                                        AS n,
       sum(cache_read_tokens)                                          AS cread,
       sum(input_tokens + cache_read_tokens + cache_creation_tokens)   AS ctx  -- 分母口径按平台 token 语义核对
FROM usage_logs
WHERE created_at >= '<start>' AND created_at < '<end>'
GROUP BY account_id ORDER BY ctx DESC;
```

命中率是 token 比率，用 token 加权，不能按请求数加权。分解方法（A、B 两个时间段，i 为账号）：

- 纯账号内效应 = Σ( ctxA_i / ΣctxA × hitB_i )：固定 A 段份额，只换成 B 段各账号的命中率；
- 纯份额效应 = Σ( ctxB_i / ΣctxB × hitA_i )：固定各账号命中率，只换成 B 段份额。

拆开之后常常看到混算掩盖的分化（有的账号已恢复、有的持续恶化），它直接决定运维动作。

## 4. PostgreSQL 事务被毒化：往上找第一条失败语句

1. 看到 `current transaction is aborted, commands ignored until end of transaction block`，
   **不要在它身上找原因**：它是次生错误，数量多、位置显眼，但根因在它上面。
2. 往上翻同一请求内更早的日志，找第一条真正失败的语句（约束违反、唯一冲突、类型错误）。
3. 事务内的「fail-open」是假的：捕获错误、打 warning、返回 nil 让调用方继续，
   但事务已经 aborted，后续每条语句都会失败。非事务上下文里它才真的 fail-open，
   所以单元测试往往全绿。
4. 典型根因：枚举 / 白名单在代码、Ent schema 的 Validate、迁移 CHECK 约束里各有一份，
   新增取值时漏了一份，注册、下单这类事务内写入违反 CHECK。修复：几处对齐，
   并写测试把代码里的权威列表和迁移里的 CHECK 列表钉在一起。

## 5. 删生产数据前，逐字节核验备份

1. 只删**已证明有副本**的东西。文件名对得上、大小差不多、时间戳吻合、「归档任务应该传过了」都不算证据。
2. 核验方法：
   - 云端和本地是同一个压缩包：比对象大小和本地 `stat` 大小；
   - 云端存的是解压后的内容、本地只剩压缩包：先 `zstd -t`（或对应的 `gzip -t`）校验完整性，
     再流式解压并计算 sha256，与云端对象的 sha256 对比；全程管道，**不落盘**
     （磁盘本来就满，落盘会让问题更糟）。
3. 把候选分三档：已证明（可删）、存疑（先验）、无副本（不动）。只删第一档，删前把清单给人确认。
4. 删之前确认文件没有被进程读写（`lsof` / `fuser`），上传中的源文件不是残留。
5. 数据库行同理：`UPDATE` / `DELETE` 前先 `SELECT` 看清目标行数，在事务里执行并核对受影响行数再提交，
   备份先行；改余额用 `balance = balance + X`，改完清对应缓存。
6. 磁盘写满的善后：先停掉写入方（迁移、导出任务），再清理；重跑任务前预留磁盘空间。

## 6. 收尾

1. 用同一组探测确认指标回到基线，撤掉临时缓解（还原开关、路由）。
2. 复盘：现象、时间线、根因、修复、防再发（测试、监控、文档）。通用经验写进 `docs/notes/`，
   站点私有部分写进私有运维仓。
3. 受影响用户的补偿：先出清单和金额，排除内部 / 聚合账号，经人批准；
   退款、补偿、批量改余额这类高危操作单独确认，一次确认不延续。
