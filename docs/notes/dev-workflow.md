# 开发流程（spec 驱动）

feature 级改动默认按以下五步推进，不必逐步征询。

## 五步

1. **先写 spec** —— 动手写码前，先用一份文档把「要做什么、按什么规则/公式算」讲清楚，分小节编号（§1/§2…）便于逐条引用。spec 是这次改动的唯一真相源。
2. **对着 spec 实现** —— 逐节按 spec 落地；关键处在代码里标注对应的 spec 小节，让实现与规格可互相追溯。
3. **写常规测试** —— 为核心逻辑与正常路径补单元测试。
4. **真实环境 + 生产形态数据的边界测试** —— 用容器（如 testcontainers 起真实 PostgreSQL + Redis）拉起真实服务依赖，灌入接近线上形态的数据，重点写**边界、并发、幂等**测试主动找 bug。这一步能抓住纯单测抓不到的资损 / 并发 / 数据迁移类严重问题。
5. **回头逐条核对 spec** —— 实现与测试完成后，拿 spec 全文（含边界场景清单）逐条核对实现「有没有完全对上」，标注每条 符合 / 偏离 / 缺失 并给出代码位置；查出偏离当场修，或带明确理由显式延后。

## 贯穿原则

- 每个阶段以「编译 + 静态检查（vet/lint）全绿」为通过门槛；改动按逻辑单元分别提交。
- **破坏性 / 改动真实数据（尤其余额、钱）的数据库迁移显式延后到上线前**：先只做代码与可回滚的加性回填；破坏性脚本留到上线前，先在副本演练 + 对账后再执行。
- 面向用户可见的页面与文案，不暴露内部机制实现细节。
- 提交信息讲清「为什么」，不只是「改了什么」。

## 为什么

spec 先行 = 「做什么」有唯一真相源；真实库 + 生产形态数据的边界测试能抓住纯单测抓不到的资损 / 并发 / 迁移类严重问题；末步逐条回核避免「写着写着偏离规格自己不知道」。
